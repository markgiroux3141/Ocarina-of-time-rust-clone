# 0028: Phase 6: Master Quest's Deku Tree, and the decomp upgraded first

- **Status:** accepted (2026-10-01); the upgrade is Phase 6's first milestone, not started
- **Date:** 2026-10-01
- **Settles:** the two questions ADR 0003 and ADR 0004 left for the first dungeon. Supersedes
  ADR 0004's pin once the upgrade lands.

## Context

Phase 6 (GAME-05, [ROADMAP.md](../ROADMAP.md)) is the first dungeon, the Deku Tree. ADR 0003
postponed which Deku Tree until then: the debug ROM (gc-eu-mq-dbg) has Master Quest's dungeons,
and the original layouts need a second ROM version with decomp support for it. ADR 0004 pinned
the decomp at `2f4c25d` (2022-10-04) and set what an upgrade must come with: a name map for the
citations, the importer's C readers fixed, every test and golden unchanged.

Since then the repo has grown to five phases of ports citing `2f4c25d`'s names: Player's
`func_808xxxxx` (several hundred), the camera's, the audio's `func_800Fxxxx`, `D_` statics,
`unk_` fields, in code identifiers (the port names its functions after the C's), comments, test
expectations and docs. The importer parses that commit's C and headers (the actor and scene
tables, `z_player.c`'s tables, `code_800EC960.c`'s, the sound effect tables, the cutscene
macros, the draw configs) and its asset XMLs.

The dungeon's code is where the old names hurt most: the dungeon actors and Player's item, shield
and combat actions are still largely unnamed at `2f4c25d` and named in later commits.

## Decision

- **Master Quest.** Phase 6 builds the debug ROM's Deku Tree (the user's choice). gc-eu-mq-dbg
  stays the only ROM (ADR 0003 holds unchanged); no second ROM version, and vanilla dungeons
  aren't a goal for now.
- **The decomp is upgraded, as Phase 6's first milestone,** before any dungeon work, to the
  decomp's current main branch at that time (its commit recorded then, in a new ADR superseding
  0004's pin). The milestone:
  1. **An address-based name map** from `2f4c25d`'s names to the new commit's: both build the
     same ROM (gc-eu-mq-dbg), so each function and data symbol has the same address in both
     builds' symbol files; the map pairs them by address (functions, `D_` and `s` statics, the
     overlays' symbols per overlay), with the struct fields (`unk_XXX`) paired by offset from
     the two commits' headers. Generated by a tool from the two checkouts, kept as a file (names
     and addresses only, no game data); ambiguous or unpaired entries are listed for review.
  2. **The citations migrated by the map**, by a script: the code's identifiers named after C
     functions and statics, comments, test names and messages, docs (the phase docs keep their
     history but get the new names where they cite code). The old name stays findable: the map
     is searchable both ways.
  3. **The importer migrated to the new layout:** the paths and names it reads (`include/`,
     `src/`, `assets/`, the asset XMLs and the extraction they now come with), the C it parses,
     the symbols the pack's record names come from (ADR 0008 keys records by decomp names: the
     ones that change get their new names, with a pack format bump).
  4. **Proof:** every test passes, and the goldens are the same bytes (same ROM, same logic);
     the pack's oracle tests run against the new commit.
- **No dungeon work starts before the upgrade.** New ports in Phase 6 cite the new names.

## Consequences

- Phase 6's dungeon ports read the decomp's current names (`Player_Action_*`, the camera's and
  the actors' named functions), and the existing ports become easier to check against it.
- The upgrade is a mechanical but wide change (most files touched); it gets its own milestone,
  commit and review, separate from any behaviour change.
- `oot.toml`'s `decomp` path moves to the new checkout, and the pack identifies the commit it
  was read from (as ADR 0004 asks).
- Until the upgrade lands, the repo stays on `2f4c25d` (ADR 0004).
